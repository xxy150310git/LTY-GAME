# 洛天依接歌词 · 锦依卫特训

一个洛天依歌词小游戏合集。**六种玩法、23 首歌、500 道题**。

游戏本体是纯前端：零框架、零依赖、零构建，双击 `index.html` 就能玩。
账号、跨设备同步、积分商店是可选的 —— 接上 Supabase 就有，不接也不影响玩。

## 快速开始

```
双击 index.html
```

不用装东西，不用起服务器，不用构建。**默认就是纯本地模式**：分数存在这台设备的浏览器里（`localStorage`），刷新、关掉重开都还在，但换设备不跟着走。

想用手机玩，随便起个静态服务器：

```bash
python -m http.server 8080
```

想要账号、跨设备同步、积分商店，见 [账号、积分与后端](#账号积分与后端)，五步就能接上。

## 六种玩法

在开始页的「玩法」里切换。前四种都是四选一，只是问法不同。

### 1. 接歌词

给出某首歌的一句上半句，从四个选项里选出下半句。

- 答对：选项变绿、显示「✓ 接上了！」，**+10 分**，1.2 秒后自动下一题
- 答错：你选的那条变红、正确的那条同时标绿、其余淡出，方便对照

### 2. 猜歌名

给出**一句歌词**（上半句或下半句随机取，避免背题），从四个歌名里猜是哪首歌。

- 题干上方会**藏起歌名标签**，否则答案直接露馅
- 干扰项从全部 23 首歌里抽，所以选项看起来都很合理
- 答对显示「✓ 猜对了！」，答错显示「✗ 这首歌是：《歌名》」
- **至少要勾 2 首歌**才能开始 —— 只勾一首的话每题答案都是它

### 3. 填空补词

从歌词里**挖掉连续的两个字**，从四个候选词里把它补回来。

> 《大氿歌》　一白忘忧再`____`
> **A.** 雪挑　**B.** 过岗　**C.** 翕张　**D.** 消愁 ← 正确

- 挖空的位置由**字符串哈希**决定，所以同一道题的空位永远是同一个 —— 答题页和导出的卷子对得上
- 优先挖**在整句里只出现一次**的词，避免挖完之后原句里还留着一样的字、说不清该填哪处
- 干扰词优先取自**同一首歌的其他句子**，不够再跨歌补；并且筛掉所有在原句里出现过的片段，避免「填哪个都说得通」
- 答对显示「✓ 补对了！」，答错显示「✗ 应该填：xxx」

> 干扰词有时是「是漫」这种被切开的片段 —— 因为全库 500 句里有 **395 句是连写的**，没有词边界可切，两字窗口是唯一可行的挖空单位。功能上不受影响：正确答案永远是唯一对得上的那个。

### 4. 找异句

四句里**三句出自这首歌，一句来自别的歌**，把不属于的那句挑出来。

> 《千年食谱颂》　哪一句不是这首歌的？
> **A.** 七星不照波月洞 ← 正确（这句是《九九八十一》的）
> **B.** 奶黄芝麻豆沙包　**C.** 就不要挣扎了 趁热吃　**D.** 嗷 猪肉炖粉条

- 题干上方**保留歌名标签**（问的就是「不是这首歌的」，所以必须知道是哪首）
- 那句外来歌词会跟本歌的所有句子做**归一化去重**，不会出现「假句其实也是这歌的」这种翻车
- 答对显示「✓ 眼真尖！」，答错会告诉你那句其实是哪首歌的

### 5. 限时狂飙

**倒计时内尽量多答**，题干和选项跟接歌词一样，但节奏快得多。

- 时长可选 **30 / 60 / 90 秒**（默认 60 秒）
- 进度位让给倒计时，**剩 10 秒时变成红底**
- 答对 / 答错的反馈停留缩短到 0.42 / 0.78 秒，不让你等动画
- 时间到自动结算，**正确率按实际作答题数算**（不是按 500 题算）
- 时间到的瞬间会清掉待跳题的定时器，不会出现「结算页被下一题盖掉」

### 6. 记忆翻牌

经典的 4 × 4 配对玩法，**8 对共 16 张牌**。

- **牌面上是一句歌词**，每首歌取**两句不同的词**各做一张牌
- **两张牌出自同一首歌就算配对成功**（两张的词长得不一样）
- 翻第二张才计一步；配对了弹一下再消除，配错了亮一会儿再扣回去
- 左上角计时、右上角步数、中间显示已配对数
- 全部配对完 → 停表 → 弹出庆祝面板 + 撒花

> 牌面**不放这首歌的专属插画**。因为每首歌有唯一插画，留在牌面上同歌两张牌图案就一样了，配对会变成「找相同图案」、根本不用看词。所以牌面只用统一的装饰图 + 加深的天依蓝，认的是词不是图。那 23 张插画挪去了「复习依下」当歌曲头图。

**每轮题数 / 时长**可自由选择（标签和单位会跟着玩法变）：

| 玩法 | 可选档位 |
|---|---|
| 接歌词 | 每轮 5 / 10 / 20 / 50 题 |
| 猜歌名 | 每轮 5 / 10 / 20 题 |
| 填空补词 | 每轮 5 / 10 / 20 / 50 题 |
| 找异句 | 每轮 5 / 10 / 20 题 |
| 限时狂飙 | 30 / 60 / 90 秒 |
| 记忆翻牌 | 固定 8 对（整栏收起） |

切玩法时如果原来那一档不被新玩法支持，会落到**这个玩法的默认档**（答题类是 10 题、狂飙是 60 秒）。
比如在接歌词选了 50 题再切到狂飙，就会变成 60 秒。

## 歌曲库与筛选

开始页点「歌曲库」打开弹窗。

- 顶部写着「本网站已收录 23 首歌曲」
- 有一个 ☑ **全部选择 / 全部取消选择**复选框，部分选中时显示半选状态
- 每行一首歌：勾选框 + 《歌名》 + 题数
- 底部是 **导出 PDF** 和 完成

**六种玩法共用同一份勾选**。摘要实时反映在入口按钮上：

| 状态 | 入口显示 |
|---|---|
| 全选 | 已选 23 / 23 首 · 共 500 题 |
| 只勾 12 首 | 已选 12 / 23 首 · 共 268 题 |
| 记忆翻牌 · 全选 | 已选 23 / 23 首 · 4 × 4 共 8 对 |
| 记忆翻牌 · 只勾 7 首 | 记忆翻牌至少要选 8 首歌哦（要凑 8 对） |

限制条件：

- **接歌词 / 填空补词 / 找异句 / 限时狂飙**：至少勾 1 首
- **猜歌名**：至少勾 2 首（否则凑不出干扰项）
- **记忆翻牌**：至少勾 8 首（8 对需要 8 首**不同的**歌，一局里同一首歌只出现一对）

不满足条件时入口那行会变红提示，开始按钮也会锁住。

## 导出 PDF

点歌曲库弹窗底部的「导出 PDF」：

- 把**当前勾选的歌曲**排成一份卷子（题干 + A/B/C/D 四个选项）
- 末尾单独放一节答案
- 然后唤起浏览器打印窗口，选「另存为 PDF」

导出内容**跟着当前玩法走** —— 猜歌名模式导出的就是「歌词 + 四个歌名选项」，填空补词导出的题干带下划线空格。

> 用的是浏览器自带的打印功能。纯前端要直接生成带中文的 PDF 得内嵌字体，不现实，打印是最稳的做法。

长卷子页数会很多（500 题很长），建议只勾几首再导。

## 复习依下

开始页的「复习依下」按钮，打开就能看**已勾选那几首歌的完整歌词**。

- 每首歌一块：该歌的专属插画 + 《歌名》 + 全部歌词
- 一句话都不少 —— 题库里每条存的是「相连的两句」且相邻两条会重叠一句，歌词单会把**两句都按顺序铺开**、重复的只算一次，所以拼出来是完整的一整首
- 去重后全库共 **749 句**
- **勾超过 6 首时**，顶部会出现一排可横向滑动的歌名胶囊，点一下滚到那首歌并高亮
- 一首歌都没勾时按钮会灰掉

> 点击「开始特训」会自动关闭歌词单。

## 计分与评价

答对一题 10 分。结算页显示总分、正确率、答对题数，还会给一句评价：

| 正确率 | 评价 |
|---|---|
| ≥ 95% | 锦依卫指挥使！歌词已经刻进 DNA 里啦。 |
| ≥ 85% | 锦依卫千户，实力相当能打。 |
| ≥ 70% | 锦依卫百户，再练练就更稳了。 |
| ≥ 50% | 锦依卫小旗，底子有了，多听几遍歌吧。 |
| ≥ 25% | 刚入门的小锦依卫，去把这几首歌循环一下～ |
| < 25% | 别灰心，先去听一遍《蝴蝶》再来！ |

## 账号、积分与后端

**默认是纯本地模式**：不配后端也能玩，分数存在浏览器里，刷新不丢。配了 Supabase 之后，账号、跨设备同步、积分商店才会启用。

### 界面入口

开始页上有**两个并排但互不相干的入口**：

| 入口 | 显示什么 | 点开去哪 |
|---|---|---|
| **账号** | 未登录显示「登录」，已登录显示昵称（绿色） | 弹窗的「账号」页：登录 / 注册 / 退出、立即同步、已拥有物品 |
| **积分** | 当前积分余额 | 弹窗的「积分商店」页：商品列表、兑换 |

两个入口共用同一个弹窗容器，只是进入时的默认页不同（弹窗标题也会跟着变）；弹窗里仍留着「账号 / 积分商店」两个页签，方便互相切换。

### 设计要点

**本地只存「答题流水」，不存「分数」。** 每答一题记一条 `{题目指纹, 玩法, 选了什么, 用了多久}`；联网后批量上传；服务端**用自己的题库副本逐条复核**，再决定给多少分。

这样做换来两件事同时成立：

- 未登录、断网都能玩，本地立刻给反馈；
- 客户端改不了分数 —— 想直接调接口加积分是行不通的，写积分只有一个入口，就是服务端的 `sync_runs()`。

题目指纹由 `questionId()` 从 `song | q | a` 算出来（两个方向各哈希一次拼起来，避免撞号），形如 `a44066-is32tw`。前端算的和 `supabase/bank.sql` 里的必须一致 —— `tools/export-bank.js` **不重写任何判分逻辑**，而是直接把 `app.js` 跑起来、调它自己的 `questionId()` 和 `rightAnswer()` 来导题库，所以两边不可能对不上（导出时会逐题校验）。

### 五步接上后端

**1. 建 Supabase 项目**

到 [supabase.com](https://supabase.com) 新建项目（免费额度：500MB 数据库 / 5 万月活），记下项目地址和 **anon public key**。

**2. 建表与安全策略**

打开控制台左侧的 **SQL Editor**，把 `supabase/schema.sql` 整个粘进去执行。
它会建 **6 张表**、开行级安全、建注册触发器、建 **4 个函数**（`handle_new_user` / `sync_runs` / `buy_item` / `use_item`），并把 6 件商品上架。

**3. 导入题库**

```bash
node tools/export-bank.js     # 生成 supabase/bank.sql
```

再把生成的 `supabase/bank.sql` 也在 SQL Editor 里执行一次。

> **以后每次改题库都要重跑这两步**，否则服务端会认不出新题，新题一律不给分。

**4. 写配置**

```bash
cp .env.example .env           # Windows 上直接复制一份改名
```

编辑 `.env`：

```
SUPABASE_URL=https://xxxxxxxxxxxx.supabase.co
SUPABASE_ANON_KEY=eyJhbGciOi...
```

**5. 生成前端配置**

```bash
node tools/build-config.js
```

它会写出 `config.js`。这个文件**要一起传到仓库**（GitHub Pages 是纯静态，只能这么给前端配置）。

脚本会做四项检查并直接拒绝：URL 或 key 里混进 `service_role` / `sb_secret_` / 数据库连接串、URL 不像 Supabase 地址、只填了一个没填另一个。其中密钥检查**不是简单查字符串** —— JWT 里的角色是 base64 编码的，脚本会解开载荷判断，光把 `service_role` 换个写法是绕不过去的。

**最后**：把 `index.html / style.css / app.js / store.js / api.js / config.js` 一起传到仓库即可（`tools/`、`supabase/`、`.env` 不需要上传）。

### 部署

后端和前端是分开的：

- **前端**：任何静态托管都行。用 GitHub Pages 的话，把上面那六个文件推到仓库、在 Settings → Pages 里选分支即可。注意 **GitHub Pages 跑不了后端**。
- **后端**：Supabase 云端，不需要自己部署。
- 两边不同域，所以记得在 Supabase 控制台的 **Authentication → URL Configuration** 里把前端域名加进允许列表。

### 环境变量与安全边界

| 变量 | 用在哪 | 能不能进前端 |
|---|---|---|
| `SUPABASE_URL` | 前端 | ✅ 公开 |
| `SUPABASE_ANON_KEY` | 前端 | ✅ 公开，靠 RLS 保护数据 |
| `service_role key` / `sb_secret_...` / 数据库连接串 | 只在服务端 | ❌ **绝对不能** |

`.env` 已在 `.gitignore` 里，不会被提交；`config.js` 可以提交。

`anon key` 本来就是发给浏览器的，别把它当秘密；真正的防线是数据库里的 RLS 和列级授权 —— 比如 `profiles.points` **根本没有给客户端写权限**，只能由 `security definer` 函数改。

### 数据表

| 表 | 作用 |
|---|---|
| `profiles` | 昵称、积分余额（客户端只读） |
| `questions` | 500 道题 + 各玩法的正确答案（客户端完全不可读） |
| `point_ledger` | 积分流水，只增不改；`ref` 做幂等 |
| `runs` | 每轮战绩，用于统计 |
| `items` | 商品目录（公开可读，改价格不用动代码） |
| `inventory` | 已拥有的物品与数量 |

### 接口

前端只用到这几个（Supabase 侧：Auth 走 GoTrue，其余走 PostgREST / RPC）：

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/auth/v1/signup` | 注册 |
| POST | `/auth/v1/token?grant_type=password` | 登录 |
| POST | `/auth/v1/token?grant_type=refresh_token` | 续期 |
| POST | `/auth/v1/logout` | 登出 |
| GET | `/rest/v1/profiles` | 昵称与余额 |
| GET | `/rest/v1/inventory` | 已拥有物品 |
| POST | `/rest/v1/rpc/sync_runs` | 上传流水，服务端复核后入账 |
| GET | `/rest/v1/items` | 商品目录 |
| POST | `/rest/v1/rpc/buy_item` | 兑换：扣分与发货在同一事务里 |
| POST | `/rest/v1/rpc/use_item` | 用掉一个消耗型道具 |

`api.js` 把它们包成 `configured / signUp / signIn / refreshSession / signOut / me / syncRuns / shopItems / buyItem / useItem`。
这些函数**都不抛异常**，统一返回 `{ ok, ... }`；没配后端或断网时返回 `{ ok:false, offline:true }`，调用方据此降级到本地逻辑。

### 防作弊做到什么程度

`sync_runs()` 里逐条复核：题目指纹在不在题库、这一题选的是不是正确项、单题耗时是否低于 **350ms**（比人手快的基本是脚本）、一批是否超过 **200 条**、24 小时内入账是否超过 **20000 分**。`buy_item()` 里余额检查和扣减写在同一条 UPDATE 的 WHERE 条件里，并发下也扣不成负数。

批次号由**批次内容**哈希得出，不是时间戳。这样同一批重复上传只会入账一次（响应丢了可以安全重发），不同批也绝不会撞号。

**能挡住**：改前端直接调接口加积分、伪造总分、重复提交同一批、脚本狂刷、重复购买永久型物品。
**挡不住**：写脚本把题目和答案预先抓下来再逐题提交 —— 这本质上是「外挂式背题」，纯前端出题的游戏没法根除，只能靠耗时下限和上限把成本抬高。要做到更强就得把题库完全收到服务端、由服务端出题，代价是彻底失去离线游玩。

`payload` 字段里存着 effect 标识（`hint5050` / `tolerance` / `reveal` / `theme` / `badge`），`use_item()` 按它判断该做什么。加新商品时照这个格式往 `schema.sql` 的 `insert into items` 里追加即可（用 `on conflict do update`，重复执行不会报错）。

> 三个消耗型道具的**实际效果还没接到答题页** —— `use_item()` 接口和数据都已就绪，下一步挂钩子即可。

### 本地存储

`store.js` 往 `localStorage` 的 `lty.state.v1` 存一个 JSON：

```js
{
  v: 1,
  anonId: "…",        // 未登录时的本机身份
  seq: 12,            // 流水自增键，同步后按它精确删除
  session: { … },     // 登录态：token 与账号信息
  answers: [ … ],     // 待上传的答题流水
  pendingPoints: 30,  // 本地已判定、还没被服务端确认的积分
  cache: { … }        // 服务端状态的只读缓存
}
```

界面上显示的积分 = `cache.points` + `pendingPoints`。
浏览器禁用存储（隐私模式）时自动降级到内存，不影响本次游玩。

## 题库格式

在 `app.js` 顶部的 `QUESTIONS` 数组里，每道题就是一个对象：

```js
{ song: "蝴蝶", q: "走吧 就算我们无法让大雨停下", a: "还有我 陪你在雨里放肆奔跑啊" }
```

- `song`：歌曲名
- `q`：上半句
- `a`：下半句（也就是玩家要选出来的那一句）

**`a` 必须紧跟 `q`** —— 它们是歌词里相连的两句，因为「接歌词」玩的就是「接下一句」。

**相邻两条会重叠一句**：第 N 条的 `a` 常常就是第 N+1 条的 `q`。
歌词单（复习依下）就是靠这个重叠关系把整首词拼回来的，所以写题库时保持这个衔接习惯，歌词单才会连贯。

## 加歌 / 加题

只需要往 `QUESTIONS` 里追加对象，**其他都不用动**：

- 歌曲库列表、题数、勾选框会自动出现
- 歌词单会自动多出这首歌
- **六种玩法全都自动用上**：接歌词和狂飙取下半句、猜歌名取一整句、填空补词挖它的词、找异句可能拿它当外来句、记忆翻牌取两句做牌

有**两处需要手动补**：

**1. 新歌要加一条插画**，否则「复习依下」里这首歌会走兜底图案：

```js
"歌名": { bg: "linear-gradient(140deg,#8ad9ff,#3aa2dd)",
        art: '<path d="…"/>' },
```

`art` 是 SVG 路径片段（`viewBox` 是 24×24，`stroke` 用 `currentColor`），`bg` 是那块小图的背景渐变。**每首歌的插画最好不一样** —— 不是为了翻牌（牌面已经不用它了），而是歌词单里一眼能认出是哪首。

**2. 改了题库要重新导一次**

```bash
node tools/export-bank.js      # 重新生成 supabase/bank.sql
```

再到 Supabase 的 SQL Editor 里执行一次。没重导的话新题在服务端认不出来、一律不给分。没接后端的话这一步可以跳过。

## 判分规则

「接歌词」原本是输入框判分，那套容错逻辑（`isCorrect()`）保留了下来，现在用于**给接歌词 / 限时狂飙挑干扰项** —— `equivalent()` 会拿它判断两个选项是不是同一句，避免出现「选哪个都对」的选项。容错从宽到严共六层：

1. 归一化后完全相同（忽略空格、全半角、中英文标点差异）
2. 去掉英文尾缀后相同（`NaYo`、`Ayo` 这种不写也算对）
3. 互为子串且长度接近（比值 ≥ 0.7）
4. 长度差太多直接判错（比值 < 0.55）
5. 编辑距离相似度 ≥ 0.82（放过错一两个字）
6. 相邻两字词组覆盖率 ≥ 0.9（核心词对得上）

## 已知限制

- **导出 PDF 依赖浏览器打印**：需要用户在打印窗口里手动选「另存为 PDF」
- **歌词为公开资料整理**：来自萌娘百科 / 百度百科 / VCPedia 等处的公开歌词，仅供学习交流
- **《九九八十一》等几首的歌词单顺序可能跳段**：因为当初出题时不是严格按全曲顺序铺的，句子是全的但次序会有跳跃
- **干扰项来自整个题库，不只是你勾选的歌**：猜歌名的选项、找异句的那句外来词，都可能出自你没勾的歌 —— 和题库总量有关，不影响判定
- **填空补词的干扰词可能是被切开的片段**（如「是漫」）：见上文该玩法的说明，是数据本身没有词边界导致的
- **限时狂飙没有中途退出**：答题页本来就没有返回键，狂飙最长 90 秒，等一下就好
- **没配后端时分数只在这台设备上**：清了浏览器数据或换设备就没了 —— 这正是接后端要解决的问题
- **道具还只做到「能兑换能展示」**：商品列表、扣分、余额、「已拥有」都通了，但提示、容错券这些**在答题页生效**的部分还没接上（`use_item()` 接口已就绪）
- **Supabase 默认要求邮箱确认**：注册后要先去邮箱点链接才能登录。想跳过去就在控制台 Authentication → Providers → Email 里关掉 "Confirm email"
- **改题库要重新导一次**：`node tools/export-bank.js` → 执行 `supabase/bank.sql`，否则服务端认不出新题
- **免费额度**：Supabase 免费档 500MB 数据库 / 5 万月活；GitHub Pages 对静态站点不限流量。这个体量的游戏远远用不到上限
